Rules (per lemma):
- INFORMAL DERIVATION: each lemma's derivation is the human-style argument that PRECEDED formalization; it may be wrong or follow a route that was never formalized. Use it only to write better exposition — the motivating idea behind a step, natural mathematical phrasing — and only where it agrees with the Lean route. Where it diverges from Lean, follow Lean and ignore it. Never import a step, constant, or claim that has no counterpart in the Lean proof.
- REVISION BRIEF: if the brief above lists findings (not the "first draft" sentinel), address each one that applies to these proofs' PRESENTATION. Faithfulness to each Lean route stays paramount and overrides any finding: never drop, reorder, or alter a load-bearing step to satisfy the referee, and keep every `% lean:` comment (invisible audit markers). Never mention the review or a revision.
- Read the Lean proof with your tools before writing; follow its structure: same case splits, same intermediate bounds, same order of argument. Collapse pure bookkeeping (measurability side goals, coercions, integrability, rewriting chains) into a sentence — bookkeeping ONLY, never a mathematical inequality, case split, construction, or constant calibration.
- SELF-CONTAINED ARGUMENT: a reader must be able to follow the proof without opening the formal development. (a) Every symbol the proof introduces gets an explicit defining display in the paper's notation at first use; a noun-phrase gloss ("X is the centered term", "the residual part") is not a definition. (b) Every step the argument leans on is STATED as the identity or inequality it is, and only then justified in a clause; naming a step or an object in place of displaying what is bounded by what is not a proof step. (c) Where the Lean route delegates to a helper with no paper environment, render that helper's CONCLUSION as a display in the paper's notation and DERIVE it at the same standard as any other step, following the helper's own Lean route (compressing only bookkeeping); a one-clause justification is enough only when the helper's proof is itself a single standard fact. Asserting a displayed bound whose derivation contains real mathematics is not a proof step. Where the helper does have a paper environment, cite it by label instead.
- SELF-CONTAINED PROSE: each proof must read as a standard mathematical argument with NO reference to the formalization in reader-visible text. Never write "Lean writes/represents…", "in Lean", "the Lean …", "the formal proof/definition/statement", "machine-checked", or "the formalization". State the mathematics directly — write "the pooled supremum equals the integral …", not "Lean writes the pooled supremum as …". Lean is named ONLY in the invisible `% lean: <decl>` comments, never in prose.
- NO LEAN IDENTIFIERS AS MATH: never put a Lean declaration name into reader-visible math — not a camelCase decl name, not a decl applied to its Lean arguments (e.g. `someSchedule α γ a c n`), not a field projection (e.g. `(someConstant …).field`), not a scaffolding alias. Use the paper's own notation from the notation table / the statement; a raw Lean identifier renders as un-mathematical text and is the clearest machine-generated tell (the `% lean:` comment is where the Lean name belongs).
- Length follows the argument, never a budget: as short as the mathematics allows, as long as self-containedness requires. Do not pad with restatement or motivation, and do not compress by dropping a display.
- Each load-bearing step ends with a LaTeX comment `% lean: <declaration name>` naming the Lean lemma/step it renders.
- Where a proof invokes another result that has its own environment, cite it by its paper label, not by Lean name.
- Use a bibliography citation inside a proof only for a source explicitly listed under that lemma's “Published cited dependencies.” Such a source is an invoked published theorem, not an assumption or contribution of this paper. Otherwise never introduce citations inside proofs.
- If the Lean route is unclear for some lemma, still start that lemma's chunk with `%% PROOF <obj_id>`, then emit `UNCLEAR: <what is unclear>` as its body and continue with the others — do not improvise a classical argument.

CROSS-REFERENCES: reference statements only through `\cref{obj:<exact-id>}` (or `\Cref` at sentence start). Cleveref supplies the kind and number, so never prefix a manual kind word and never use legacy `\ref{...}` for any target. Use the literal environment id, including any kind prefix, never note-style P-/T-/A-/L- numbering. Never write a bare obj_id or emit `\label{obj:...}` yourself.
