=== IF A TARGET IS TOO STRONG (do NOT fake or silently weaken) ===

If a target is not provable AS STATED (false, or true only on a narrower regime), do not write a hand-wavy proof and do not silently edit the claim. Emit a `proposed_statement_change`:
  `{id, current:"<claim now>", proposed:"<narrowed claim>", reason:"<why the current is too strong / what breaks>", direction:"narrow"}`
Only `direction:"narrow"` exists — narrowing a genuinely-too-strong claim toward a true one. NEVER weaken a claim merely to make your proof close (laundering; rejected and escalated). If you have ALSO proved the PROPOSED claim, emit that proof in `proofs` with `"argues_proposed": true` (banked provisionally, attached when the change is applied as proposed); such a proof must argue the proposed text exactly, and without the flag (or if adjudication modifies the proposal) the target reopens. Emit an `open_obligation` only when even the honest narrowed claim does not close.

NEVER SUBSTITUTE THE CLASS. Narrowing to a smaller class is legal in general, but NOT when the class is a PUBLISHED one the note's positioning depends on: proving the claim on a class of your own construction does not settle the question posed on theirs, and silently retreating there turns the result into an analogue while the prose still claims the settlement. If the target does not close on the published class, the `proposed_statement_change` `reason` must name the EXACT published condition that blocks it and state whether the new class is a subclass, superclass, or incomparable — a converse proved on a SUBclass transfers up and should be restated there; an achievability does not.
NEVER ASSUME THE CRUX. A legitimate narrowing RESTRICTS the regime / quantifier / scope. It must NOT promote the node's own hard, unproven step into a HYPOTHESIS ("Suppose [the hard property that delivers X] …; then [a trivial reduction]" — e.g. assuming a least-favorable family already has bounded χ² and the required separation and doing only the Le Cam reduction). If the construction's key property is genuinely open, KEEP the node stating the RESULT with the construction as an explicit OPEN PROOF OBLIGATION (status stays to-prove); an assume-the-crux narrowing is rejected.

=== IF A CONSTRUCTED-OBJECT DEFINITION IS MIS-SPECIFIED (the real bug is the formula, not the claim) ===

When a claim like `X = O_P(U_n(λ))` has the right SHAPE but the defined construction `U_n` (an envelope, a rate functional, an exponent) omits terms your decomposition proves are there, the honest fix is to CORRECT THE DEFINITION, not to narrow the theorem. Emit a `proposed_definition_change`:
  `{id:"def:...", current:"<construction now>", proposed:"<corrected construction>", reason:"<what the proof shows the true formula is>", direction:"correct"}`
RULES: only a CONSTRUCTED-OBJECT definition (one with a formula / `inputs`), NEVER a class (`by_member_properties`) — class membership is a scope move, not a formula fix. `direction` is always `"correct"`. NEVER gerrymander a definition to your proof's convenience objects (laundering, the dual of weaken-to-prove).

HARD RULE (definition-vs-statement). When your proof shows a target holds only with a referenced constructed object F replaced by a CORRECTED formula, you MUST emit a `proposed_definition_change` for F. Do NOT narrow the STATEMENT to inline a different expression — that leaves the core INCOHERENT (downstream rate functional / exponent / phase results still reference the old F). A statement narrowing is for LOGICAL CONTENT that is too strong; a definition correction is for a mis-specified FORMULA.

PROPAGATE the correction. You solve the whole dependency cluster at once: when a corrected definition forces others (envelope ⟹ rate functional ⟹ rate exponent / phase map), propose EACH corrected definition together and PROVE the downstream targets against them, re-deriving any changed optimization explicitly. If a re-derivation is genuinely intractable, narrow THAT downstream statement to a conditional form rather than abandoning the cluster. The goal is one coherent core, not a root flag with everything downstream open.

=== IF A TARGET IS A GENUINE OPEN GAP (you cannot close it, and no honest narrowing exists) ===

A PARAMETERIZED RATE IS A CLOSED RESULT, NOT AN OPEN GAP. A bound whose exponent is an explicit FUNCTION of the model's declared structural / nuisance / smoothness exponents, or the VALUE of an explicit optimization over the estimator's own tuning parameter (clip / trim / bandwidth / sieve dimension), IS a complete result: PROVE it in that parameterized form and mark it `proved`. Do not punt it to `open_obligation` or degrade it to a fragment because the exponent is not a single absolute constant — that is the conservatism failure this guard stops. The only honest residual is whether the exponent is TIGHT (matches the converse), recorded as a residual `oeq:`, never as the achievability being open. State the dependence on auxiliary rates and the sub-regimes where it meets / loosens from the converse.

A FROZEN ARTIFACT ASSERTING OPENNESS IS NOT EVIDENCE OF OPENNESS. If a frozen definition / note says a target is "open" / "not derivable" / "no exponent fixed", DISREGARD that editorial claim and DERIVE the result anyway: the frozen core binds the QUESTION, never whether the answer exists. `open_obligation` is a LAST RESORT for a step that genuinely needs a NEW IDEA, never justified by a frozen artifact's say-so.

When a target is true and correctly stated but a load-bearing step genuinely does NOT close from the frozen primitives (it needs a new strategy, a literature result to adapt, a reframing), do not assume it, do not degrade the claim, do not leave it silently unproven. Emit an `open_obligation` that ISOLATES it:
  `{node_id, what_is_open:"<the precise sub-claim/construction not closed>", obstruction:"<why it doesn't close from the primitives>", attempted:"<route(s) you tried, so guidance doesn't repeat them>", partial_result:"<strongest sub-result proved so far>"}`
Leave that node `to-prove`; the orchestrator supplies a DIRECTION via a directive on the next solve, so be precise about the obstruction and what you tried. Prove everything else; one obligation per genuinely-open node.

ALWAYS RECORD YOUR BEST PARTIAL RESULT in `partial_result` (a weaker-but-proved bound, all but one step, the result under one extra flagged condition). It is fed back next round as "PRIOR PARTIAL PROGRESS — EXTEND, do not restart"; when you receive such progress, BUILD ON IT, never re-derive it.
